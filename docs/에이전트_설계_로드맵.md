# 왜 에이전트인가 · 셀링 포인트 · 로드맵 (심사 + 팀 공용)

> "왜 이게 AI/에이전트 서비스인지, 무엇이 차별점인지, 무엇부터 채워야 하는지"를 한 문서로. (갱신: 2026-07-26)
> 계산 세부는 `docs/계산로직_및_아키텍처.md`, 값 검증은 `RESEARCH.md`.

---

## 1. 한 줄 정의
> **전월세 만기(D-90)라는 강제된 결정의 순간, KB가 3갈래(갱신·이사·매매)를 당신의 상황·소비패턴으로 통역해 '결정의 첫 관문'이 된다.** — 계산기가 아니라, 결정을 함께하는 도우미.

## 2. 왜 "에이전트"인가 — 핵심은 '라우팅'

**규칙 = 사람이 인코딩(각 경우의 정확 계산). 에이전트 = 어떤 규칙을 어떻게 적용할지 판단.**

```mermaid
flowchart LR
  IN["상황(계약·재무·주택유형)"] --> SUP
  SUP["🧭 supervisor (라우팅)<br/>· 어떤 규칙 세트? (주택/오피스텔…)<br/>· 어떤 갈래가 현실적?"] --> CALC["🔒 결정론 계산<br/>(선택된 규칙 세트)"]
  CALC --> NAR["🤖 개인화 통역 + verify 루프"]
  SUP -. "규칙값은 사람이 리서치해 인코딩<br/>(에이전트가 지어내면 할루시네이션 = 금지)" .-> RULES["rules/*.yaml"]
```

- **경우의 수 폭발**(주택유형 × 규제 × 생애최초 × 소득 × 주택수 …)을 하드코딩 if문으로 감당 불가 → **에이전트가 "어떤 규칙 세트/갈래를 적용할지" 라우팅**. 계산은 여전히 결정론.
- 경우의 수가 늘수록(오피스텔·연립·다주택 …) **라우터의 가치가 커진다** = 이 아키텍처가 존재하는 이유.

**구현된 에이전틱 요소 (정직하게 3가지):**
1. **supervisor 라우팅** (`agents/supervisor.py`, graph `route` 노드) — 규칙 세트 선택(주택 wired, 오피스텔 seam) + 갈래별 현실성 판단. 분석 그래프가 이제 **intake→compare→route→narrate 4노드**로 Langfuse에 찍힘.
2. **자기검증 루프** (`core/verify.py`) — LLM 출력에서 facts 밖 숫자·권유 감지 → **스스로 재생성**(최대 2회). "판단→행동→검사→재시도" = 에이전트 핵심 루프.
3. **상황 적응형 통역** — 같은 계산도 페르소나(월세/신혼/청년…)·라우팅 노트에 따라 다른 산출물.

> **정직한 경계**: 라우팅·계산은 결정론(안전), LLM은 통역·자기검증에만. "완전 자율 에이전트"가 아니라 **금융을 위한 책임감 있는(bounded) 에이전트** — 이게 심사에 더 강한 포지션.

## 3. 셀링 포인트 (KB 상품성)
1. **결정 순간 선점** — 세입자는 만기 때 은행을 '결정하는 곳'으로 안 떠올림(부동산·네이버로 감). 이 서비스가 **최고 의도(intent) 시점에 KB를 first-touch**로 → 대출·상품이 경쟁사 아닌 KB로.
2. **KB 소비데이터 해자** — '온라인 발품'(이 동네에서의 하루)을 카드/소비 데이터로 초개인화 → 직방·토스가 **복제 불가**.
3. **안전한 금융 AI** — 숫자는 결정론+출처+verify. "은행이 생성형 AI를 책임감 있게 쓴다"는 신뢰.
4. **실행 연결** — "디딤돌 가능"에서 끝이 아니라 KB 상품·상담예약까지. 계산은 훅, **전환이 본질**.

## 4. MCP 필요한가? → **아니오 (지금은 과함)**
- MCP는 **외부 도구를 표준 프로토콜로 연결/상호운용**할 때 쓴다(별도 서버 도구, 여러 클라이언트 공유 등).
- 우리 라우팅은 **내부 규칙 세트 선택** — LangGraph 조건분기로 충분. MCP를 끼면 in-process 도구에 불필요한 프로토콜 계층만 추가.
- **쓸 수도 있는 미래**: 외부 실시간 도구(예: 국토부·카카오·청약 API)를 여러 에이전트가 공유하게 되면 그때 MCP 검토. 현재는 `tools/`(순수 함수)로 충분.

## 6. 데이터 니즈 (사람이 구해야 하는 것 — 항목화)

### 6-A. ✅ 규정값 검증 완료 (PR #22, 2026-07-26)
증액상한·통보기한·이사비·**중개보수(구간표)**·**취득세(지방세법 §11 3단계 구간)** 모두 팀원이 법령 검증·구현. `renewal.yaml`·`one_time.yaml` `checked_at: 2026-07-26`. → 시작 시 미검증 경고 0.

### 6-B. 🟡 동네 대표 데이터 (`data/region_facts.yaml`, 발품용)
9개 regionId × {교통·장보기·카페먹거리·여가·물가}. **가이드: `docs/지역데이터_채우기_가이드.md`**. 출처: 카카오맵·ODsay·참가격.

### 6-B-2. 🔴 빌라(연립·다세대) HUG 요율 검증 (2026-07-26 결정)
**주택유형 범위 확정: 아파트 + 빌라(원룸·투룸·빌라=연립·다세대)만.** 오피스텔(준주택)·단독다가구는 제외.
- 근거: 아파트·빌라 둘 다 법적 "주택"이라 **세금·대출 규정 동일**(코드 무변경). 차이는 HUG 보증료 요율뿐.
- 단독다가구 제외: HUG 반환보증료가 건물 전체 근저당·선순위 보증금까지 봐야 정확 → 실거래 데이터로 계산 불가.
- **채우는 곳:** `rules/guarantee_hug.yaml`의 `other`(=빌라) 요율. 현재 detached와 동일한 placeholder → **연립·다세대 실제 요율 HUG 공시 대조 필요.** (compare는 `housingType`로 이미 분기 완료, 값만 검증하면 됨)
- 지역 후보를 빌라 실거래 시세로 필터(D 파이프라인)는 후속(현재는 아파트 시세 기준).

### 6-C. 🔴 오피스텔(준주택) 규칙 세트 — 매매 갈래 확장 시 (순위 5)
> 주택과 **다른 법조문·세율·대출**이라 통째로 새 리서치 필요:
- **취득세**: 지방세법 §11-7 일반세율(~4%대) — 주택특례(§11-8, 1~3%) 대상 아님. 세율표·부가세(지방교육세·농특세) 확인.
- **생애최초 취득세 감면**: 지특법 §36의3 "주택" 대상 → 오피스텔 적용 여부 확인(제외 가능).
- **정책대출**: 디딤돌·버팀목은 주택 대상 → 오피스텔 자격/대체 상품(준주택 담보대출) 확인. `policy_loans.py` 분기.
- **LTV·규제·주택수**: 오피스텔(주거용/업무용) LTV·규제지역·주택수 산정 특례 확인. `lending_regulated.yaml` 확장.
- **UX 카피**: 매매 헤드라인 "내 집" 내러티브 → 오피스텔 포함 시 문구 재검토.
- 반영처: `agents/supervisor.py::RULE_PROFILES["오피스텔"]`(현재 `supported:false` seam) + 새 계산 분기.

### 6-D. 🔵 KB 소비데이터 (`agents/spending_profiles.yaml` 교체)
가구별 가정 프로필 → KB 카드/소비 세그먼트로 교체(같은 shape). 해자의 핵심.

## 부록 — "왜 굳이" 반박 대비 (심사 Q&A)
- **"계산기랑 뭐가 달라?"** → 계산기는 한 값만. 우리는 ①만기 시점에 3갈래를 한 저울로 ②전문성 장벽 제거 ③당신 삶으로 통역(발품) ④KB 실행 연결.
- **"이거 그냥 규칙 프로그램 아냐?"** → 계산은 규칙(맞고, 그래야 안전). 에이전트는 **경우의 수 라우팅 + 자기검증 + 적응형 통역**. 규칙과 에이전트의 역할 분리가 핵심 설계.
- **"왜 오피스텔은 안 돼?"** → 준주택은 세금·대출이 통째로 다른 규칙 세트. 지금은 범위 밖으로 정직하게 두되, **라우터가 있어 규칙 세트만 붙이면 확장**(순위 5).
