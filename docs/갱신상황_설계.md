# 갱신 상황 인식 설계 — enum + 결정표 + resolver

> 실행값 기준 커밋: `0e85354`(2026-08-01). 관련: [에이전트_설계](에이전트_설계.md) · [아키텍처](아키텍처.md)

갱신 경로의 **이해 단**. 자유입력의 계산 불가 사정(실거주 거절·전월세 전환·통보기한 경과 등)을
닫힌 enum으로 분류하고, 결정표로 계산·안내를 조합한다.

```
자유입력 → [AI 분류만] 닫힌 enum → [사람] HITL 승인 → [규칙 resolver] 결정표 조합 → 계산·안내
```
LLM은 **분류만**. guidance·citation·힌트 문구는 **yaml 원문 그대로**(재작성·생성 금지). 조합은 결정론.

---

## 1. 상황 enum (7종, 닫힘)

| id | 계산 효과 | 근거 조항 |
|---|---|---|
| `notice_deadline_passed` | cap_pct 0 (묵시적 갱신, 인상 0%) | 주임법 제6조 |
| `renewal_right_exhausted` | cap 해제(상한 미적용 가능) + 경고 | 제6조의3 제1항 |
| `jeonse_to_monthly` | 전월세전환율 상한 적용(감액분→월세) | 제7조의2 |
| `landlord_self_occupancy` | 계산 불변, 안내만 | 제6조의3 제1항 8호·제5항 |
| `term_change` | 계산 불변, 안내만 | 제4조 |
| `simple_increase` | cap_pct 5 (기본) | 제7조 |
| `unknown` | **계산 미반영** → `consultNote` 원문 전달 | — |

`unknown`은 결정표(`renewal_cases.yaml`)에 없다 — 안전한 실패(계산 안 바꾸고 상담 창구로).

## 2. 결정표 구조 (`rules/renewal_cases.yaml`, 6케이스)

각 케이스: `priority` · `requires` · `effect` · `guidance` · `citation` · `branch_hint`.

| id | priority | effect |
|---|---|---|
| notice_deadline_passed | 100 | `cap_pct: 0` |
| renewal_right_exhausted | 90 | `cap_pct: null, warn` |
| jeonse_to_monthly | 80 | `apply_conversion_cap` |
| landlord_self_occupancy | 70 | `{}` |
| term_change | 60 | `{}` |
| simple_increase | 10 | `cap_pct: 5` |

resolver 반환 7필드: `cap_pct` · `effects` · `guidances` · `citations` · `applied` · `rejected` · `branchHints`.

---

## 3. 조합 규칙 (`tools/renewal_resolver.py`, 결정론)

- **cap_pct = 우선순위 승자독식** — 여러 상황이 상한을 건드리면 priority 최상위 케이스 하나만 적용.
  (예: 통보경과 cap 0 + 권소진 cap null 동시 → priority 100인 통보경과가 이겨 cap 0)
- **guidance·citation·branchHints = 누적** — 승인·통과한 모든 케이스가 쌓인다.
- 승인 0건(또는 전부 기각) → 기본 `simple_increase`(cap 5) = 현행 동작. **골든패스 불변.**

## 4. `requires` 교차검증 = 안전장치

LLM 분류를 **계약 사실과 대조**해 불일치면 기각한다. 자유입력만으로는 계산이 바뀌지 않는다.

- 실행값 예: 자유입력에 "통보 없었어요"가 있어 `notice_deadline_passed`를 승인해도,
  `noticeDaysLeft = 73`(만기 미래)이면 → **기각**, cap 5 유지(갱신 금액 불변).
  기각 사유는 `resolver.rejected`에 기록. (`test_renewal_resolver.py`)

## 5. branchHints — 상황이 3갈래에 갖는 의미 (표시 계층)

상황 인식 결과가 갱신 카드에만 갇히지 않도록, 3갈래(renewal/move/purchase) 각각에 힌트를 붙인다.
`tone` 4종(favorable·uncertain·consider·neutral), applied 케이스만, 문구는 yaml 원문.
예: `landlord_self_occupancy` → 갱신 `uncertain`("실거주 이유로 거절할 수 있어 갱신이 확정적이지 않아요")
/ 이사·매매 `consider`("갱신이 막힐 경우를 대비해 함께 보세요"). **계산·순위·탭 순서는 무변경.**

---

## 6. 확장 경계 (발표 과장 방지)

**yaml만으로 되는 것** (코드 무변경):
- cap_pct 효과 · 안내(guidance) · 근거(citation) 문구 · priority
- 기존 사실 키(`noticeDaysLeft`) 기반 `requires`
- `branch_hint`(tone·문구)

**코드가 필요한 것**:
1. `requires`에 **새 사실 키**(예 renewalUsed·계약기간) → resolver `facts`에 그 키 공급 필요
2. **새 effect 종류**(cap_pct/warn/apply_conversion_cap 외) → compare 연동 코드
3. **8번째 enum** → 스키마(`RenewalSituation`)·프론트 타입 동시 변경

---

## 7. 전환 계산 (`jeonse_to_monthly`)

보증금→월세 전환(주임법 §7-2). `월세 증가분 = 감액분 × 전환율 ÷ 12`.
전환율은 `rules/renewal.yaml conversion_rate = 0.0475`(4.75% = `min(기준금리 2.75% + 대통령령 2.0%p, 10%)`,
`checked_at 2026-07-26`). cap_pct(인상률)와 **독립** — 둘 다 승인되면 각각 적용.
감액분 미입력이면 안내만(계산 불변). ⚠️ 보증료는 원 보증금 기준 유지(보수적 표기, [아키텍처 §5](아키텍처.md) 한계).
