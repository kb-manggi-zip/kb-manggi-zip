## 6. 동네 태그(region_enrich.yaml) — 기준과 근거 (2026-07-31)

`backend/scripts/refresh/build_region_tags.py`가 `region_enrich.yaml`(6구 80개 동)의 `tags`/`source`를
자동 산출한다. 전부 **"80개 동 중 상위 25%"** 상대 기준으로 통일 — 절대 임계값을 쓰면 서울 6구
데이터 특성상 대부분의 동이 걸려 변별력이 없어짐(예: 지하철역 반경 500m 이내=64%, 공원 반경
800m 이내=97% — 아래 참고).

| 태그 | 근거 데이터 | 기준 |
|---|---|---|
| 카페거리 / 마트·편의점 밀집 / 여가시설 밀집 / 학원가 | SBIZ 반경상가 집계(`trades_store.region_facts`, §5) | 해당 카테고리 카운트가 80개 동 중 상위 25%(3분위 이상) |
| 초역세권 | 카카오맵 Local API 카테고리검색(`SW8`=지하철역, 반경 3km 내 최근접) | 최근접역 거리가 80개 동 중 최근접 상위 25%(1분위 이하) |
| 공원 인접 | 카카오맵 Local API 키워드검색("공원", 카카오에 공원 전용 카테고리 없음 — `category_name`이 "여행 > 공원"인 것만 인정) | 최근접공원 거리가 80개 동 중 최근접 상위 25% |

**"역세권" vs "초역세권" 이름을 나눈 이유**: "역세권"은 실생활에서 절대적 의미(반경 500m≈도보10분
이내)로 통용되는 표현이라, 상대기준(상위 25%)으로 계산한 값에 그 이름을 그대로 쓰면 뜻이 달라짐.
그래서 상대기준 결과는 "초역세권"으로 새로 이름 붙이고, 원래 "역세권"은 사람이 직접 확인해 붙인
수기 태그 7개 동에서만 유지(둘 다 붙을 수 있음 — 서로 다른 주장이라 모순 아님).

**초기 버전에서 발견·수정한 문제 2가지**:
1. 절대기준(boolean: "반경 안에 하나라도 있으면 O") 최초 버전은 위에서 설명한 변별력 문제로 폐기 →
   상대기준으로 교체.
2. `scoring.py::_facts_count()`가 `region_facts.value_json`(사람이 읽는 문장, 예: `"반경 500m 내
   마트·편의점 186곳"`)에서 정규식으로 **첫 번째 숫자**를 뽑고 있었는데, grocery 필드만 실제 개수보다
   "500"(반경)이 문장 앞에 나와서 **항상 500으로 오독**하는 기존 운영 버그를 발견(§5 카운트가 전부
   이 값을 참조). DB에 이미 있던 정수 `count` 컬럼을 직접 읽는 `trades_store.read_region_fact_counts()`를
   추가해 대체 — 이 문서의 §5 상권 데이터 신뢰도와도 직결된 수정이라 함께 기록.

**임의 작문 금지 원칙 적용**: 기존 수기 태그 중 source에 근거 문장이 없거나(`"학교"`) source와
실제로 안 맞는 것(`"경전철"` ← source는 "7호선"=지하철, 경전철 아님)은 확인 후 제거·수정.
"주택가"는 근거를 만들 수는 있었으나(상권 4지표 전부 하위 25% → 추정) 직접 측정이 아니라
**부재로부터의 추론**이라 다른 태그들보다 근거가 약해 채택하지 않고 제거.

## 제안 (2번 반영 완료 · 1·3번 미반영, 팀 판단 필요)

**1. 자녀유무보다 소득분위 — 🔴 재검토 후 보류(2026-07-30)**. 통계보고서 표10 "경상소득" 행 실측:
저소득(1,2분위)과 고소득(9,10분위)의 이사 사유 차이가 직주근접 +13.4%p, 자녀양육·교육 +5.0%p로, 신혼
세그먼트 차이(2.7%p)보다 훨씬 큼. 초안은 `finance.annualIncome`이 이미 폼에 있어 스키마 변경 없이
바로 쓸 수 있다고 봤으나, 재검토 결과 두 가지 문제로 보류:
1. **원래 문제를 안 풀어줌** — 표10의 소득분위 비교는 전체 인구 기준(자녀 유무로 층화 안 됨)이라,
   "고소득층이 자녀양육·교육을 더 신경씀"이 실제로는 "고소득층에 자녀 있는 가구 비율이 더 높아서"인
   confound일 수 있음. 즉 "자녀 있으면 학군 중시"(§3, 여전히 🔴)를 증명도 대체도 못 함.
2. **균등화 문제** — 제대로 분위를 매기려면 가구원수가 필요한데 폼에 없어 스키마 변경 필요(초안의
   "스키마 변경 없음" 전제가 틀렸음). 정확한 10분위 원 경계값도 아직 미확보.
효과 대비 비용 판단: 신혼 케이스 기준 가중치 변화가 1~2%p 수준이라 순위에 미치는 영향도 작음 — 데모
이후 폼 개편 등으로 스키마를 만질 일이 생기면 그때 재검토.

**2. 통근 가중치(0.561) 재계산 — ✅ 2026-07-30 반영 완료(팀 승인)**. 원안(3축 균등분배)은 "뭉친 25.5%를
쪼개는 순간 그 비율이 임의값이 된다"는 한계 때문에 팀 논의 중 폐기하고, **분할 없이 그대로 consumption
축에 대응**시키는 방식으로 대체 구현: `score_preference()`가 실제로 재는 건 "구 필터 매칭"이라 편의
시설·공원 성격과 무관하고, `score_consumption()`(상권·편의시설 밀집도 매칭)이 개념상 정확히 대응하기
때문. 결과: commute=0.306(직주근접 단독, 확정) / consumption=0.255(교통편리·편의문화시설·공원녹지
전체, 확정 — 기존 0.24 근사를 대체). budget·preference는 이번 건과 무관, 근사 그대로.
