# 하루시뮬(SC-07) 씬 이미지 생성 계획

> 상태: 초안 — 팀 확인 후 실행(비용이 한 번에 나가는 오프라인 배치라 사전 합의 필요)
> 관련: `feat/gemini-connection`(API 연동 준비), `backend/data/region_enrich.yaml`(태그), `frontend/src/data/scenes.ts` / `backend/app/agents/scenes.yaml`(현재 스톡사진 — **가라 구현, 구조 포함 전부 교체 대상**)

## 1. 지금 상태 (참고용, 구속력 없음)

`DayPlayer.tsx`(SC-07)는 화면 틀만 있고 5개 시간대 씬(🌅아침·☕오전·☀️점심·🌇저녁·🌙밤) 스톡사진을 순서대로 넘기는 가라 구현이다. 갈래(이사/매매/갱신)끼리도 이미지 URL이 동일(캡션만 다름), 지역 커스텀도 82개 동 중 3개뿐이고 그마저 이미지는 스톡사진이다. **개인화는 지금까지 100% 텍스트(캡션)였고, "5개 시간대 고정" 구조 자체도 새 설계의 전제가 아니다** — 아래 §2가 새 구조.

## 2. 핵심 설계 원칙 — 두 개의 레이어를 분리한다

논의 중 나온 핵심 문제: "이 사람이 중시하는 축 위주로 보여주자"만 하면 **같은 사람에게 추천된 3개 후보 동이 전부 똑같은 이미지**가 되어버린다(축은 사람 기준이지 동 기준이 아니라서). 반대로 "동 태그 위주로만" 하면 그 사람에게 뭐가 중요한지 반영이 안 된다. 그래서 레이어를 나눈다:

| 레이어 | 기준 | 결정하는 것 | 비용 |
|---|---|---|---|
| **콘텐츠(이미지 자체)** | 동(region) | 어떤 장면이 그려지는가(카페거리 vs 마트 vs 일반) | 생성 비용 발생(§6) |
| **배치(노출 순서·개수·강조)** | 사람(페르소나 축 우선순위) | 몇 개를 어떤 순서로, 뭘 크게 보여줄까 | **0원**(프레젠테이션 로직만) |

이 사람의 축 우선순위는 이미 계산되고 있다 — `persona.build_persona()`의 `weights`/`priorities`(통근·소비·예산·선호지역, 국토부 이사사유 4축 기반). 이걸 새로 만들 필요 없이 그대로 가져다 쓰면 된다.

### 2-1. 콘텐츠 카테고리(동 기준, 5개 — "시간대"가 아니라 "축+태그" 매핑)

시간 이모지는 자연스러운 하루 흐름을 위해 유지하되, 각 자리는 특정 태그/축에 대응한다:

| 카테고리 | 대응 축 | 매칭 태그 | 있을 때 | 없을 때(폴백) |
|---|---|---|---|---|
| 🌅 통근 | 통근 | 초역세권 | 지하철역 입구 장면 | 골목길 걷는 장면 |
| ☕ 상권-카페 | 소비 | 카페거리 | 카페 밀집 거리 | 카페 한 곳 |
| ☀️ 상권-여가 | 소비 | 공원 인접 | 공원 장면 | 일반 식당가 |
| 🌇 상권-생활 | 소비 | 마트·편의점 밀집 | 시장/마트 거리 | 저녁 골목 |
| 🌙 집/동네 | (배경) | 학원가·여가시설 밀집 | 학원 불빛 거리 / 체육시설 야경 | 일반 주거지 |

- **예산·선호지역 축은 씬으로 안 만든다** — 예산은 이미 SC-08(아낀돈)이 전담, 선호지역은 "그 동을 골랐다"는 사실 자체가 반영이라 별도 이미지 근거가 약함.
- 동마다 이 5개 카테고리를 다 만들어두되(82동×5=410장, §6 그대로), **노출 시엔 동이 실제로 가진 태그 개수만큼만 보여준다** — 태그 0개 동은 통근+집 정도로 짧게(2~3씬), 태그 많은 동은 최대 5씬. 고정 5씬이 아니라 **동마다 가변**.

### 2-2. 배치 로직(사람 기준, 신규 — 추가 이미지 비용 없음)

`priorities`(1순위 축)에 따라 **콘텐츠는 그대로 두고 순서·강조만** 바꾼다:

- 1순위 = **통근** → 통근 씬을 맨 앞 + 크게(히어로)
- 1순위 = **소비** → 상권 3종(카페/여가/생활) 중 그 동이 실제로 가진 태그부터 앞에 배치, 통근은 뒤로
- 1순위 = **예산/선호지역** → 시각화할 축이 아니므로 배치 변화 없음(기본 순서: 통근→상권 3종→집)

같은 사람이 후보 3개 동을 볼 때 → **셋 다 "소비"가 앞에 오는 배치는 같지만, 그 안의 실제 이미지(카페거리냐 마트냐 일반이냐)는 동마다 다름** — 이렇게 두 문제(사람 개인화 vs 동 차별화)가 동시에 풀린다.

## 3. 최종 스코프

**82개 동 × 5카테고리 = 410장 생성**(갈래·페르소나 무관 공용, 이유는 §4). 노출은 동·사람 조합마다 가변(2~5씬) — 생성은 최대치로 미리 다 해두고, 보여줄 때만 추리는 방식.

## 4. 여전히 유효한 기존 결론

- **갈래(이사/매매/갱신) 무관**: 물리적 거리는 계약 형태로 안 바뀜 — 캡션(`caption1`/`caption2`)만 갈래별 유지, 이미지는 공용.
- **페르소나(가구유형)별 이미지 분기 안 함**: 사람 개인화는 §2-2의 배치 로직 + 기존 텍스트 내레이션(`narrator.narrate_lifestyle`)이 담당. 사람이 나온다면(뒷모습) 가구유형 무관 중립 묘사 하나로 통일.

## 4-1. 논의 포인트 — 랜드마크 명칭(역·공원 이름)을 캡션에 반영할지

**현재 3개 동(망원·홍제·보문) 커스텀 씬은 캡션에 실제 랜드마크 이름을 쓴다** (예: "망원역 6호선", "한강공원 망원지구"). 82개 동으로 확장하면 이걸 유지할지가 논의 필요.

- **이미지엔 넣지 않는다(확정)**: AI 생성 이미지는 "합정역"이라고 프롬프트에 넣어도 실제 합정역이 그려지지 않음 — 가짜를 진짜처럼 보이게 하는 것이라 L1 원칙("공공 랜드마크 명칭은 캡션 텍스트로만, 이미지·서술로 사실 단정 금지")에 위배. §5 템플릿대로 이미지는 계속 일반화된 분위기만.
- **캡션엔 넣을지 = 미결정, 팀 논의 필요**: 넣으면 지금 3개 동과 톤이 일관되고 신뢰도↑, 대신 82개 동 전부 이름 검수(오타·폐업/개명 등) 부담이 생김. 안 넣으면 태그 문구("역세권·카페거리 등")로만 서술 — 검수 부담은 적지만 3개 동만 유독 구체적이라 톤이 안 맞을 수 있음.
- **데이터는 지금 미리 확보 추천**: `build_region_tags.py`가 카카오 API에서 이미 `place_name`(예: "합정역 2호선", "마포새빛문화숲")을 받아오는데 지금은 거리 계산에만 쓰고 버림 — "쓸지 말지"와 무관하게 **이름 저장은 지금 필드 하나 추가하면 공짜**(같은 API 호출 재사용). 안 해두면 나중에 82개 동 API를 다시 호출해야 함. 사용 여부는 나중에 정하더라도 데이터는 지금 갖춰두는 걸 추천.

## 5. 프롬프트 템플릿

```
Photorealistic photo, {lighting}, {scene_visual}, in a Seoul residential/commercial
neighborhood street. A person is seen from behind, {activity}, no visible face,
neutral clothing (household-agnostic). Low-rise Korean buildings, natural everyday
atmosphere, DSLR photo quality, no text, no logos, no specific real signage.
```

| 변수 | 값 출처 | 예시 |
|---|---|---|
| `lighting` | 카테고리 고정값(5개) | "early morning warm sunlight" / "midday bright sunlight" / "golden hour evening light" / "warm night streetlights" |
| `scene_visual` | §2-1 매핑표(태그 있으면 구체적, 없으면 일반) | "a subway station entrance with morning commuters" |
| `activity` | 카테고리 고정값(5개, 갈래·페르소나 무관) | "walking toward the station" / "holding a coffee cup" / "sitting on a park bench" / "carrying a grocery bag" / "walking home" |

`region_name`(동 이름)은 **프롬프트에 직접 넣지 않는다** — "그런 느낌"을 만드는 것뿐이라, 지명을 넣으면 특정 장소를 사실처럼 그렸다고 오해할 수 있음(L1 원칙: 실제 랜드마크 명칭 단정 금지).

## 6. 실행 계획

1. `scripts/generate_scene_images.py` 신규 작성 — `region_enrich.yaml`(82동 tags) 순회 → 동×5카테고리 프롬프트 조립 → Gemini 호출 → `backend/data/scene_images/{region_id}_{category}.png` 저장
2. 저장 경로를 `backend/app/agents/scenes.yaml` + `frontend/src/data/scenes.ts`에 채워넣기(이미지는 카테고리 키로, 실제 노출 순서·개수는 §2-2 배치 로직이 런타임에 결정 — 이 부분은 프론트/narrator 쪽 별도 구현 필요, 스키마 변경 있음)
3. 갈래별 캡션은 기존 방식 유지
4. 실패/재시도 로깅(refresh 스크립트들과 동일 패턴)

## 7. 비용

| 스코프 | 장수 | 비용(표준) |
|---|---|---|
| **채택안**: 82동×5카테고리, 갈래·페르소나 공용 | 410 | 약 2.2만원 |
| (미채택) 자녀유무만 2분기 | 820 | 약 4.4만원 |
| (미채택) 페르소나 전체(4종) | 1,640 | 약 8.8만원 |

§2-2(사람별 배치 로직)는 이미 계산된 `priorities`를 재사용하는 프레젠테이션 로직이라 **추가 생성 비용 0원**. 1회성 비용 — 재생성 안 하면 추가 지출 없음.
