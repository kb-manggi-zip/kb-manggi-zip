# 하루시뮬(SC-07) 씬 이미지 생성 계획

> 초안 — 팀 확인 후 실행(비용이 한 번에 나가는 배치라 사전 합의 필요)

## 뭘 만드는가

SC-07 "하루시뮬"은 지금 화면 틀만 있고 5개 시간대 씬을 Unsplash **스톡사진**으로 채운 가라 상태(갈래 3개끼리도 같은 사진 재사용, 지역 커스텀은 82개 동 중 3개뿐). 이걸 **동네마다 실제로 다른 AI 생성 이미지**로 바꾸는 계획.

## 핵심 구조 — 고정 3씬(아침·점심·저녁), 내용만 동마다 다르게

씬 개수는 **고정 3개**(가변 아님). 이유: 개수가 가변이면 "태그 많은 동 = 씬 많음 = 왠지 더 매력적으로 보임"이라는 착시가 생김(실제 순위는 스코어링이 이미 매기는데, 씬 개수가 또 다른 신호처럼 보이면 왜곡). 고정 3개면 이 착시가 없다.

### 개인화 근거 — 어떤 데이터를 왜 쓰는지

하루시뮬 개인화는 성격이 다른 두 데이터를 합쳐서 만든다:

| 데이터 | 무엇을 결정하나 | 소스 |
|---|---|---|
| **상권데이터**(SBIZ 반경상가 집계) | **그 동이 뭘 가졌는지**(씬 콘텐츠) — 음식점·카페/마트/여가시설/학원가 밀집도 → 동네 태그 | `trades_store.region_facts` → `region_enrich.yaml` |
| **마이데이터**(개인 실측 소비) | **이 사람에게 뭐가 중요한지**(씬 순서·강조) — 카페/배달/식비/쇼핑/여가 중 또래보다 많이/적게 쓰는지 | `persona.consumptionSignals`(`rules/consumption_baseline.yaml` 기준). `RegionList.tsx`의 leadSignal, 화면에 뜨는 "실측 카페 적게 쓰는 편" 같은 문구랑 같은 소스 |

**왜 둘 다 필요한가**: 상권데이터만 쓰면 사람 개인화가 없고(모두에게 순서가 똑같음), 마이데이터만 쓰면 동네 차별화가 없다(추천된 3개 동 이미지가 다 비슷해짐). 씬 콘텐츠는 상권데이터로 동마다 다르게, 씬 순서·강조는 마이데이터로 사람마다 다르게 — 이렇게 나눠야 둘 다 성립한다.

**한계(정직하게)**: 마이데이터 쪽 카테고리 분류(카페/배달/식비/쇼핑/여가)는 `rules/consumption_baseline.yaml`에서 **아직 검증 안 된 PoC 근사치**(`checked_at: null`, 실제 카드사 통계 아님)로 정의돼있다. 하루시뮬 개인화도 그 위에 얹히는 만큼 같은 한계를 그대로 물려받는다 — 여기서 새로 만드는 문제는 아니고 기존 시스템의 기존 TODO(별도 검증 필요)이며, 이 문서는 "이미 있는 신호를 재사용한다"는 선에서 그친다.

### 씬 배치

- **통근 씬은 초역세권 있는 동에서만 만든다**(80개 동 중 20개). 역 없는 동에 억지로 "통근" 자리를 채우면 배경도 사람도 특별할 게 없어서 아무 정보가 안 됨 — 그럴 바엔 그 자리에 **그 동이 실제로 가진 콘텐츠 태그를 하나 더** 보여주는 게 낫다.
- **초역세권 있는 동**: 통근(역 장면, 사람은 출근 가방·바쁜 걸음으로 표현) + 콘텐츠 태그 상위 2개 = 3씬.
- **초역세권 없는 동**: 콘텐츠 태그(음식점·카페 밀집/공원 인접/마트·편의점 밀집/학원가/**여가시설 밀집**) 상위 3개(있는 만큼) = 3씬. 콘텐츠 태그가 3개 미만이면 있는 만큼만(가변) — 이건 "이 동은 딱히 두드러지는 게 없다"는 정직한 반영.
- 어느 쪽이든 **어떤 태그를 우선 보여줄지**는 이 사람의 소비신호(마이데이터)로 정한다.

**뭘 기준으로 매칭시켰나**(마이데이터 신호 → 동네 태그): 아래 둘 중 하나를 만족해야만 매칭시켰다 — ① 신호 카테고리와 태그가 애초에 같은 데이터(예: 식비/카페 → SBIZ `dining_cafe` 필드가 실제로 음식점+카페를 합산한 값), ② 개념이 직접 대응(예: 여가→여가시설). 둘 다 아니면 근사치로 표시하고, 아예 없으면 매칭 안 함(임의로 갖다 붙이지 않음).

| 신호 | 매칭 | 확실성 | 근거 |
|---|---|---|---|
| 카페 많이 쓰는 편 | 음식점·카페 밀집 우선 | ✅ 직접 대응 | 카테고리 자체가 동일 |
| 식비 많이 쓰는 편 | 음식점·카페 밀집 우선 | ✅ 같은 데이터 | SBIZ `dining_cafe` 필드가 음식점+카페 합산 |
| 여가 많이 쓰는 편 | 여가시설 밀집 우선 | ✅ 직접 대응 | 카테고리 자체가 동일 |
| 쇼핑 많이 쓰는 편 | 마트·편의점 밀집 우선 | ⚠️ 근사치 | "쇼핑"은 옷·온라인 등도 포함하지만, 그나마 제일 가까운 물리적 상권이라 사용 |
| 배달 많이 쓰는 편 | 매칭 없음 | — | 배달은 동네 밀집도와 무관(어디서든 시켜먹음) |

매칭되는 신호가 있으면 그 태그를 먼저 배치, 남은 자리는 그 동의 나머지 보유 태그로 채운다. **매칭 자체가 없으면(배달 신호이거나 신호가 없을 때)** 기본 순서(음식점·카페>공원>마트>여가>학원가, 잠정)로 폴백.

→ 정리: **씬 개수는 고정 3개**(착시 방지) + **그 안의 콘텐츠는 동 기준**(태그) + **어떤 걸 먼저 보여줄지는 사람 기준**(소비신호) — 세 가지가 동시에 성립한다.

## "동마다 실제로 달라지나?" — 카테고리는 5개뿐인데

카테고리(장면 종류)는 통근+상권 5종(카페/공원/마트/여가/학원가)뿐이지만, **이미지는 카테고리별로 82개 동이 나눠 쓰는 게 아니라 동마다 따로 생성**한다. 같은 "음식점·카페 밀집" 카테고리라도:
- 동마다 별도 이미지 생성(파일 공유 안 함)
- 프롬프트에 그 동의 실제 수치(카페·음식점 356곳 vs 300곳 등)를 넣어 "북적임 정도"를 다르게 표현 가능

다만 한계는 인정한다 — 유한한 카테고리로 무한한 동네를 완전히 다르게 그릴 순 없고, 예산대가 비슷해 실제로 특징이 겹치는 동네는 이미지도 비슷하게 나올 수 있다. **이건 왜곡이 아니라 정직한 반영**(비슷한 동네를 억지로 다르게 그리면 그게 오히려 임의 작문). "이 동네가 맞다"는 확신은 이미지가 아니라 동 이름·실측 통근분·실거래가 같은 텍스트가 담당 — 이미지는 분위기만.

## 갈래·가구유형은 이미지에 안 나눔

- **갈래(이사/매매/갱신)**: 물리적 거리는 계약 형태로 안 바뀜 — 캡션(`caption1`/`caption2`)만 갈래별, 이미지는 공용.
- **가구유형별 이미지 자체는 안 나눔**(비용 3~4배) — 대신 위 §핵심 구조의 "점심·저녁 우선순위" 로직으로 사람 개인화를 반영 + 기존 텍스트 내레이션이 나머지를 담당.

## 스코프·비용

**통근(초역세권 있는 20개 동만) 20장 + 콘텐츠 태그 합계 101장 = 121장.**
"고정 3"은 **화면에 보여주는 개수**일 뿐, **미리 만들어두는 이미지 개수는 아니다** — 그 동이 가진 태그 전부를 미리 만들어둬야, 사용자마다 다른 태그를 우선시해도(§씬 배치 매칭표) 보여줄 이미지가 항상 있다. 상위 2개만 미리 만들면 그 2개에 안 든 태그를 원하는 사람에겐 보여줄 이미지가 없어짐(설계 구멍, 발견 후 수정). 역세권 아닌 동에 억지 "통근" 자리도 만들지 않아서(§씬 배치) 181장보다 더 줄었다.

OpenAI `gpt-image-1`(medium quality) 기준 장당 약 $0.04 추정 — 실제 계획(127장, 동 61개) 기준 약 **$5(7천원대)**. 1회성 비용. 정확한 단가는 실행 시점 OpenAI 요금표 참고.

## 실행 방법

1. `backend/scripts/generate_scene_images.py`(작성 완료, dry-run 기본):
   - `region_enrich.yaml`의 80개 동 순회
   - 동마다: **초역세권 있으면** 통근 프롬프트 1개(역 장면, 인물 없음) 추가 + **그 동이 실제로 가진 콘텐츠 태그 전부**(카페/공원/마트/여가/학원가 중 있는 것 전부, 개수 제한 없음) 프롬프트 조립 → OpenAI `gpt-image-1` 호출 → `backend/data/scene_images/{region_id}_{category}.png` 저장. 실제 계획: 127장(동 61개).
   - `.env`에 `OPENAI_API_KEY` 없으면 `--run`을 줘도 호출 안 하고 에러(실비용 호출 차단). 기본 실행은 dry-run(계획·비용만 출력).
2. 저장 경로를 `backend/app/agents/scenes.yaml` + `frontend/src/data/scenes.ts`에 태그(카테고리)별로 채워넣기 — 동 하나에 이미지가 여러 장(통근+태그별) 매핑됨
3. **노출 시점(런타임)**: 사용자의 마이데이터 신호로 §씬 배치 매칭표를 적용해 그 동이 가진 이미지들 중 정확히 3개(통근+2)를 골라 보여줌 — 이 선택 로직은 프론트 또는 narrator 쪽에 새로 구현 필요(현재 미구현, 별도 작업)
4. 갈래별 캡션은 기존 방식 유지(이미지와 무관)
5. 실패/재시도 로깅(refresh 스크립트들과 동일 패턴)

## 이미지엔 랜드마크 이름 안 넣음

"합정역"이라고 프롬프트에 넣어도 실제 합정역은 안 그려짐 — 이미지는 계속 일반화된 분위기만. **캡션(텍스트)에 실제 역·공원 이름을 넣을지는 미정**(지금 3개 동 커스텀 씬은 이미 그렇게 함). 이름 데이터(카카오 API의 `place_name`)는 사용 여부와 무관하게 지금 저장해두는 걸 추천(같은 API 호출 재사용, 나중에 다시 부르는 것보다 쌈).

## 프롬프트 뼈대

인물 없음(결정: 씬 간 일관성·페르소나 고정관념 문제 회피). 텍스트/간판을 못 넣는 대신(글자 깨짐·가짜 상호 문제),
"한눈에 한국 동네"로 보이게 하는 건축·거리 요소(다세대·빌라 저층 건물, 노출된 가스 배관, 얽힌 전깃줄, 좁은 골목+밀착
주차, 옥상 물탱크, 흐릿하게 처리된 간판)를 공통으로 넣는다.

```
Photorealistic photo, {카테고리별 조명 + 장면}, South Korean low-rise mixed-use neighborhood
buildings, exposed gas pipes, tangled overhead power lines, narrow street with tightly parked
cars, rooftop water tanks. No people in frame. No readable text, no logos, no real signage.
```

실제 프롬프트는 `backend/scripts/generate_scene_images.py`의 `_SLUG_DESC`/`_KOREA_CUES` 참고(단일 소스).

## 고민 중인 것들 (팀 확인 필요)

- **여가시설(헬스장·노래방·관광명소 등 뭉뚱그린 카테고리) 씬을 어떻게 그릴지 — 결국 "차라리 랜드마크(실제 역·공원 이름)를 보여주는 게 낫지 않나"가 고민의 본질.** 세부 업종까지 나눠 그리는 것보다, §랜드마크 활용 여부부터 정하는 게 먼저일 수 있음 — 결론 아님.
- **랜드마크 이름을 캡션에 쓸지**: 이미지엔 절대 안 넣지만(§이미지엔 랜드마크 이름 안 넣음), 텍스트(캡션)엔 실제 역·공원 이름을 넣을지 미정. 데이터(카카오 `place_name`)는 사용 여부와 무관하게 지금 저장해두는 걸 추천.
- **점심·저녁 우선순위 로직**: 소비신호(leadSignal) 매칭 규칙(§표) 동의 여부, 매칭 없을 때 기본순서(음식점·카페>공원>마트>여가>학원가, 잠정) 동의 여부.
- **가구유형별 이미지 분기**: 안 하는 것으로 잠정 — 동의 여부.

**실행 전 필수**: 실제 이미지 생성(OpenAI API 호출)은 진짜 비용이 나가는 단계라 사람이 직접 결제·실행해야 함 — 계획만 짜둔다고 자동으로 생성되지 않음.
