# PART A. ODsay 통근시간 연동 (상권 API와 동일 방식)

> "당신 직장까지 대중교통 N분"은 부동산 앱이 못 하는 개인화의 핵심.
> 키 있으면 실데이터, 없으면 파이프라인만 완성 → 키 넣으면 자동 채워짐 (상권 API 패턴 그대로).

## A-1. tools/transit.py 신규
- ODsay 대중교통 길찾기 API (lab.odsay.com)
- .env의 ODSAY_API_KEY (없으면 폴백 모드)
- 함수 commute_minutes(from_lat, from_lng, to_lat, to_lng):
    · ODsay 대중교통 경로 → 총 소요시간(분) + 환승 횟수
    · 키 없거나 실패 → 직선거리 기반 추정 + "예상치" 플래그 (지도 API 폴백 원칙 동일)
- persona의 직장/주요거점 좌표 ↔ 동네 center 좌표로 계산

## A-2. persona에 직장 좌표
- personas.ts에 workplace 필드: P1/P2/P3 각각 직장 위치(좌표)
    예: P2 신혼 → 여의도(금융권), P1 청년 → 강남, P3 → 판교 등 (페르소나 설정에 맞게)
- region_facts 발품에 "직장까지 N분" 주입

## A-3. 저장·런타임 (상권 API와 동일)
- 결과를 region_facts DB에 transit 필드로 캐싱 (동네×직장 조합)
- refresh 스크립트에 통근시간 수집 추가, 런타임은 DB만 읽음
- 오프라인 재현: demo 스냅샷에 포함

## A-4. narrator 반영
- 발품 서사에 "○○역에서 회사까지 28분, 환승 1번" 자연스럽게 삽입
- 갈래·페르소나별로 이 정보가 의미있게 (매매=장기 통근, 이사=통근 개선 등)

# PART B. 실제 가능 시나리오 역추출 ★ 발표의 뼈대

> ⚠️ 핵심 원칙: 발표 시나리오는 우리가 상상해서 만들지 않는다.
> **현재 코드·데이터로 실제 끝까지 돌아가는 경로만** 시나리오로 인정한다.
> 코딩 에이전트가 코드를 근거로 아래를 채운다.

## B-1. 페르소나 × 갈래 매트릭스 — 실제 완주 가능한 것 표시
각 조합이 현재 코드로 처음부터 끝까지(진입→비교→상세→발품→금융→저장) 돌아가는지:

| 페르소나 | 계약 | 갈래 | 완주? | 막히는 지점 |
|---|---|---|---|---|
| P1 청년 | 전세/월세 | 갱신 | [?] | |
| P1 청년 | 〃 | 이사 | [?] | |
| P1 청년 | 〃 | 매매 | [?] | |
| P2 신혼 | 전세 | 갱신 | [?] | |
| P2 신혼 | 전세 | 이사 | [?] | |
| P2 신혼 | 전세 | 매매 | [?] | |
| P3 월세 | 월세 | 갱신 | [?] | |
| P3 월세 | 월세 | 이사(전세갈아타기) | [?] | |
- 각 [?]를 [완주 OK / 부분 / 막힘]으로 판정 + 막히면 어느 SC·어느 함수에서인지

## B-2. 각 완주 경로의 "계산 계보" 추적
완주 OK인 경로마다, 어떤 계산이 실제로 실행되는지 코드 기준으로:

```
예시 형식 (P2 신혼·전세·매매):
[입력]  연소득 8천 / 자본 6천 / 전세보증금 3.2억 / 만기 D-89 / 생애최초 '예' / 만35세미만
   ↓ SC-02 → store
[지역판정]  classify_region("마포구") → {metro:T, regulated:T}   ← rules/regions.yaml
   ↓
[매매 계산]  calc_buy()
   자본 = 6천 + 3.2억(보증금) = 3.8억
   디딤돌 자격? 신혼·무주택·소득8천≤8.5천 → O, 한도 3.2억, 금리 2.85%   ← policy_loans.yaml
   LTV = 생애최초·규제지역 → 70%                                    ← lending_regulated.yaml
   DSR = 40%, 스트레스 +3.0%(수도권규제) → 산정금리 7.1%             ← dsr
   캡 = min(LTV한도, DSR한도, KB 3억, 정부 6억)                      ← mortgage_cap
   max_price = ? (실제 계산값)
   월부담 = 디딤돌분 + KB분 혼합                                     ← rates
   취득세 = 생애최초 감면 -200만                                    ← one_time.yaml
   ↓
[동네]  regions(branch=매매, budget=max_price) → 마포/은평/도봉 중 예산내
   ↓ trades.db 실거래 필터
[발품]  narrator(P2, 신혼, 매매, 선택동네) + 통근시간 + 상권 + 실거래사례
   ↓
[금융]  products(매매, 생애최초) → 디딤돌+KB주담대+화재보험+청약   ← kb_products/*.md
```

- 이 계보를 **완주 가능한 경로 전부**에 대해 작성
- 각 단계에 실제 참조되는 rules 파일·함수명 명시 (발표에서 "이 숫자는 이 근거"를 말하기 위함)

## B-3. 발표 골든패스 추천
- B-1/B-2 결과 중, **가장 임팩트 있는 1개 메인 + 1개 서브** 추천:
    · 메인 후보: P2 신혼·매매 (규제3겹·디딤돌·생애최초가 다 보이는 경로)
    · 서브 후보: P3 월세·전세갈아타기 or P1 갱신 (다른 갈래·다른 감정)
- 추천 근거: 어느 경로가 우리 셀링포인트(만기·규제·개인화발품)를 가장 잘 보여주는가
- 각 골든패스의 예상 소요(데모 시간), 클릭 순서, 화면별 하이라이트 포인트

## B-4. 데모 리스크 점검
- [ ] 골든패스가 오프라인(네트워크 끊김)에서 완주되는가 — demo.db·캐시로
- [ ] LLM 호출 실패 시 폴백(템플릿)으로라도 완주되는가
- [ ] 각 화면 전환에 걸리는 시간 (버벅임 없는가)
- [ ] "데모 데이터 채우기" 버튼으로 입력 시간 단축되는가
