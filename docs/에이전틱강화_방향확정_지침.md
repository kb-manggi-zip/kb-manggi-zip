# 에이전틱 강화 방향 확정 & 코드 점검 지침
### "책임 있는 에이전트" — 자율(A) 아닌 아키텍처(B)로 대상 노리기

> 결정: **하네스로 자율성을 푸는 방향(A)은 채택하지 않는다.** 금융 서비스이고 심사위원이 KB 현직자이므로,
> 우리의 무기("숫자는 코드가·규제3겹·확인 못하는 건 못한다고 말함")는 **통제된 에이전트**에서만 성립한다.
> 대신 **에이전트가 정당하게 필요한 4곳을 명확히 하고, 그곳을 깊게** 만든다.

---

# PART 0. 에이전트 정당성 — "왜 여기 LLM인가"를 코드로 증명

각 노드가 왜 규칙이 아니라 에이전트여야 하는지, 코드에 근거가 있는지 점검:

| 노드 | 에이전트인 이유 | 규칙이면 안 되는 이유 | 점검 |
|---|---|---|---|
| 문진 명확화 | "여의도 근처" 같은 모호 입력 해석 | 무한한 자연어 변형을 if로 못 잡음 | [ ] planner가 되묻는가 |
| 계약서 이해 | 포맷 제각각 문서 | 정규식으로 모든 계약서 파싱 불가 | [ ] Vision 노드 존재 |
| 발품 서사 | 소비×동네×갈래 조합 서술 | 조합 폭발 — 템플릿으로 자연스러움 불가 | [ ] narrator가 매번 다른가 |
| 상품 사유 | RAG 결과를 개인 맥락에 연결 | 상품×조건 설명을 하드코딩 불가 | [ ] matcher가 사유 생성하는가 |

**반대로 — 계산은 절대 에이전트化 금지 (점검):**
- [ ] compare/LTV/DSR/보증료가 순수 함수인가 (LLM 경유 0)
- [ ] LLM 출력에 숫자가 있으면 facts와 대조 검증하는가

> 발표 논리: "판단 4곳 = LLM, 돈 계산 = 도구. 이 경계가 금융 에이전트의 형태다."

# PART 1. 후보군 동적화 점검 — "9개 고정"인가 "필터 결과"인가 ★

> 실거래 9개가 문제가 아니라, **그게 사용자 조건으로 추려진 것인지**가 문제.

- [ ] regions가 사용자 예산(compare 결과)으로 **실제 필터링**되는가, 아니면 고정 9개 노출인가
- [ ] 필터 로직: 예산 이내 실거래가 있는 동 → 거래량·여유 정렬 → 상위 N (이게 되어 있는가)
- [ ] 갈래별로 다른 후보가 나오는가 (매매 예산 vs 전세 예산 vs 월세)
- [ ] 페르소나별로 후보가 달라지는가 (P1 청년 예산 vs P2 신혼 예산 → 다른 동네)
- 판정:
  - 고정 9개면 [문제] → 예산 필터 연결 필요
  - 필터 결과면 [OK] → 후보 수는 9개든 상관없음 (오히려 "예산에 맞는 곳만" 이 정직)

## 확장이 필요하다면 (조건부)
- 현재 6개 구 → 사용자 희망지역 입력을 받는다면 그 구까지 확장 (refresh_deals에 구 추가)
- 단, **무한 확장 금지** — "서울 전역"보다 "예산·희망지역 교집합"이 맞음
- 데모는 3 페르소나가 각각 다른 동네를 받는 것만 보이면 충분

# PART 2. 만기 특수성 부각 — 이 서비스만의 것

> "집 찾기 서비스"가 아니라 "만기 결정 서비스"임이 계속 느껴져야 함.

- [ ] 통보기한 D-day가 긴박감 있게 표현되는가 (단순 표기 넘어)
- [ ] 갱신 갈래에 "지금 안 하면 자동갱신/묵시적갱신" 맥락이 있는가
- [ ] 만기 시점의 **금융 이벤트**가 부각되는가 (전세대출 만기=재약정/대환 시점)
- [ ] 발품·비교가 "2년 후 또 이 시험을 본다"는 반복성을 건드리는가 (갱신 vs 매매의 본질 차이)
- 제안: 만기 특수성을 살리는 카피/브리핑 — "이번 만기는 눌러앉기, 다음 만기엔 살 수 있을까요?" 같은 시간축

# PART 3. 개인화 발품 강화 — 대상을 가르는 지점 (가장 약함)

## 3-1. 있는데 안 쓰는 데이터부터 (신규 수집 전)
- [ ] trades.db 실거래를 발품에 쓰는가 — "지난달 이 동네 이 평형 N억 거래" (있는데 안 쓰면 낭비)
- [ ] 상권 집계를 "밀집도 해석"으로 쓰는가 — "카페 47곳"(나열) → "걸어서 커피 고르기 좋은"(의미)
- [ ] enrich 좌표로 통근시간 계산하는가

## 3-2. 통근시간 = 개인화 발품의 핵심 (ODsay)
- [ ] persona에 직장/주요거점이 있는가
- [ ] "당신 직장까지 대중교통 N분"이 발품에 나오는가
- [ ] 미연동이면: ODsay 붙이면 바로 개인화 강화 (좌표 이미 있음) — 우선순위 높음
- 이게 "온라인 발품"의 진짜 야무진 부분 — 부동산 앱은 못 해주는 것

## 3-3. 소비패턴 → 발품 반영
- [ ] persona 소비성향(외식·카페·차량)이 씬 선택을 바꾸는가
- [ ] scene_rules가 공개되는가 (왜 이 씬인지 설명 가능 — 숨긴 가중치 없음)
- 예: 무차량+카페선호 → "역세권·카페거리" 씬 / 차량+자녀 → "주차·마트·공원" 씬

## 3-4. 하루 서사 구조
- [ ] 시간축(아침→저녁)으로 구성되는가
- [ ] 갈래별 관점 차등 (매매=자산 / 이사=환경 / 갱신=아낀돈)
- [ ] 발품 끝 → 비교표/금융 재연결 (순환)

# PART 4. (설계 비전만 — 구현 안 함) MCP·확장성

> 마감 리스크로 구현하지 않되, 발표 로드맵으로 언급할 수 있게 구조만 확인:
- [ ] 도구(compare·regions·products)가 독립 함수로 분리돼 있는가 (나중에 MCP 서버화 가능한 구조)
- 발표 문장: "각 도구를 MCP로 분리하면 KB 내부 여신심사·상품DB와 표준 프로토콜로 연결됩니다"
- ⚠️ 지금 MCP 구현 착수 금지 — 마감까지 AI레이어·발품·발표가 우선

# 보고 형식
1. PART 0: 4개 노드 에이전트 정당성 [OK/부족] + 계산 순수성 확인
2. PART 1: 후보군이 [고정 9개 / 예산필터 결과] 중 무엇인가 — 근거 코드
3. PART 3: "있는데 안 쓰는 데이터" 목록 + 통근시간(ODsay) 연동 여부
4. 대상 관점 **가장 약한 고리 Top 3**
5. 개인화 발품 강화 구체안 3가지 (기존 데이터 우선, 신규는 리드타임 표기)

# 절대 원칙
- 자율 에이전트(A) 아님 — 통제된 아키텍처(B)
- 계산은 규칙, 판단만 LLM
- 후보는 "많이" 아니라 "예산에 맞게"
- 발품 facts는 실데이터, 서술만 LLM
- 새 기능·MCP는 제안/비전만, 구현은 사람 승인
- 넓히지 말고 깊게
