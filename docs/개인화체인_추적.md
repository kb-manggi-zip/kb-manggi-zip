# 개인화 체인 전수 추적 (코드 사실 = 발표 Q&A 단일 진실 소스)

> "소비 데이터 → 페르소나 → 동네 추천/발품/지출"의 전 체인을 코드로 추적한다. **코드 변경 없음.**
> 각 단계에 `파일:함수` + P2(신혼) 실행값. 최하단 **N6 불일치 표**가 이 감사의 결론이다.

## ⚠️ 먼저: N6 불일치 요약 (결론부터)

| # | 문서/발표 주장 | 코드 사실 | 판정 |
|---|---|---|---|
| 1 | 소비 성향이 **동네 점수**에 반영된다 | `score_consumption`은 **dining_cafe(식음료)만** 사용. 장보기·여가는 수집만·미반영 | **부분참**(식음료 축만) |
| 2 | **장보기 성향은 다른 하루**를 받는다 | narrator엔 **세그먼트 traits만** 들어감. 신혼 세그먼트엔 '장보기'가 없음(그건 자녀). 실측·진술 미전달 | **과장** |
| 3 | **실측이 세그먼트를 덮어쓴다** | `values_food_override`+`consumptionSignals`에서 덮어씀 ✓. 단 **순위 변화는 실측≠세그먼트일 때만** | **참(조건부)** |
| 4 | 확정 전 신호는 **어떤 계산에도 안 실린다** | 미확정 → `noteAdjust={}`, `note_weights` hold, `held` | **참** |
| 5 | **분석 질문은 사람마다 다르다** | LLM이 P2≠P1로 질문 생성 확인 ✓. **단 동적 SQL은 전부 폴백**(아래 N4) | **참(질문만)** |
| 6 | **문장 속 숫자는 원본과 대조된다** | `numbers_grounded` 존재하나 **어떤 caller도 `allowed_numbers`를 안 넘김 → 비활성** | **과장(메커니즘만 존재)** |
| M0 | (실거래 데이터) | ✅ **국토부 실거래 실데이터 64,496건**으로 교체됨(O1, `refresh_deals.py` 실수집). 통근·상권도 실측 스냅샷 | **해결** |

**한 줄**: 개인화 *로직*은 실재하고 결정론·통제돼 있다. 그러나 (a) 소비→동네 반영은 **식음료 한 축뿐**,
(b) narrator는 **세그먼트만** 받음, (c) 동적 T2SQL 결과는 **폴백**, (d) 숫자 verify는 **미활성**, (e) 순위
변화는 **후보가 차별화될 때만** 보인다. 발표는 이 경계 안에서만 주장해야 안 뚫린다.

## N1. 소비 데이터의 두 용도 — 분리 확인

| | (A) 성향 파이프라인 | (B) 지출 여력 분석 |
|---|---|---|
| 읽는 것 | `mydata.demo.db`(transactions) 카테고리 비중 | `mydata.demo.db`(transactions) 지출 |
| 계산 주체 | **결정론 배치** (`derive_personal_traits`: 비중÷baseline, ±30%) | **T2SQL** (`spend_query`: LLM 질문/SQL + 가드레일) |
| 출력 종착 | `scoring_ctx`(values_food·weights) → 동네점수/페르소나 | 리포트 ⑤(월평균·고정·변동여력·주요지출) |
| 코드 | `app/tools/personal_traits.py` | `app/agents/spend_query.py` |

**공유 지점**: 둘 다 **같은 DB(transactions)를 `spend_query.guarded_execute`로 읽는다**
(A의 `aggregate_category_ratio`도 이 함수 사용). **데이터소스+실행함수는 공유, 계산·출력은 분리.**

## N2. (A) 성향 파이프라인 전수 (P2 신혼 실값)

**1) 세그먼트 기본값** — `narrator.profile_for(household)` ← `agents/spending_profiles.yaml`
- 구조: 가구별 `traits`·`keywords`·`workplace`. 근거: **경기 카드소비 연령대 근사**(파일 주석, "개인화 아님").
- P2 실값: traits=`["주말 나들이·숙박 지출","유아용품·유아교육 준비 지출 시작","인터넷쇼핑 비중 큼"]`,
  keywords=`["투룸","대형마트 근접","주말 나들이 코스"]`, workplace=여의도(금융권).

**2) 개인 실측 도출** — `tools/personal_traits.py::derive_personal_traits(pid)`
- 입력: 합성 거래 카테고리 비중 ÷ `rules/consumption_baseline.yaml`, **±30% 임계** 넘으면 override.
- P2 실값: `{카페: low(0.65), 배달: low(0.61), 쇼핑: high(1.4)}` → `values_food_override = False`(식음료 낮음).

**3) 진술(HITL)** — `agents/clarify.py`
- `clarify()` → `weightAdjust`(축 배수). 사용자가 SC-14에서 확정 → `contract.noteAdjust`에 저장.
- **미확정/상충(held)이면 `noteAdjust={}`** → 계산에 미반영. (저장: 확정분=noteAdjust, held는 프론트 상태)

**4) 페르소나 조립** — `tools/persona.py::build_persona`
- `consumptionSignals` = [세그먼트]+[실측 override]+[진술 noteSignals], 각 항목에 **source 태그**("세그먼트"/"실측"/"진술").
- 스코어용: `scoring_ctx` → `values_food = values_food_override(실측)`, `weights = note_weights(household, note, noteAdjust)`.

## N3. (A) 소비 성향의 소비처 3곳 — 실제로 뭐가 들어가나

### ① 동네 소비축 점수 — `tools/scoring.py::score_consumption`
- **오직 `dining_cafe`(음식점·카페 수)만** 점수에 들어간다(`_dc_count` → `region_facts['dining_cafe']`).
- 소비 카테고리 ↔ 상권 필드 매핑:

| 소비 신호(성향) | 매핑 상권 필드 | 점수 반영? |
|---|---|---|
| `values_food`(카페·배달·식비) | `dining_cafe` | ✅ 반영 |
| 장보기 성향 | `grocery`(수집됨) | ❌ 미반영 |
| 여가 성향 | `leisure`(수집됨) | ❌ 미반영 |

- 식: `values_food=True → density`, `False → 0.4+0.3·density` (density=min(dc/200,1)).

### ② narrator(발품 서사·자막) — `agents/narrator.py::build_lifestyle_prompt`
- 프롬프트에 들어가는 건 **`profile_for(household)`의 `traits`·`keywords` = 세그먼트만**.
- **실측 override·진술 noteSignals는 narrator에 미전달**(E1 확인). L4에서 "소비성향×상권 facts 연결 문장" 지시 추가했으나, 그 소비성향도 **세그먼트 traits**다.

### ③ 페르소나 카드 — `screens/RegionList.tsx`, `ProfileConfirm.tsx`
- `consumptionSignals`를 출처 배지와 함께 표시. RegionList는 **실측·진술만 겉에**, 세그먼트는 "추천 기준 보기"로 접음.

### ★ 핵심 판정: "장보기 지출 높은 신혼 → 장보기 동선의 하루"
- **①점수**: 거짓 — 장보기(grocery)는 점수 미반영.
- **②서사**: 부분참에 가깝지만 실제론 어긋남 — narrator는 세그먼트 traits를 받는데 **신혼 세그먼트엔 '장보기'가 없다**(그건 자녀 traits "정기 장보기 비중 큼"). 신혼은 "대형마트 근접"(keyword)·"인터넷쇼핑"(trait). 실측 '쇼핑 high'도 narrator엔 안 감.
- → **이 주장은 자녀 가구엔 서사 층위에서만 성립, 신혼엔 데이터상 성립 안 함.** 발표에서 예시를 **자녀×외식/장보기**로 바꾸고 "서사 층위(세그먼트 기반)"로 한정해야 정확.

## N4. (B) T2SQL 지출 분석 전수

**1) 질문 생성** — `spend_query.py::_llm_questions(persona_ctx, branch)`
- persona_ctx(가구·계약·note)를 LLM이 보고 1~3개 질문. **P2/P1 실제로 다르게 생성**:
  - P2(신혼): "이사 관련 카테고리 지출 추이?", "전세 일회성 지출?" 등
  - P1(1인 재택): "주거 is_fixed 지출?", "관리비·공과금 월평균?" 등
- → "질문은 사람마다 다르다" **참**.

**2) 가드레일 7종** — `spend_query.py`
| # | 구현 | 차단 예시 |
|---|---|---|
| 1 SELECT만 | `_validate_sql_text` + `_authorizer` | `DELETE...` → 파서 거부 |
| 2 테이블 화이트리스트 | authorizer `ALLOWED_TABLE='transactions'` | 다른 테이블 READ → DENY |
| 3 컬럼 화이트리스트 | authorizer `ALLOWED_COLUMNS`(7개) | 미허용 컬럼 → DENY |
| 4 persona_id 슬롯 | `re: persona_id\s*=\s*:pid` 필수 | 슬롯 없으면 GuardrailError |
| 5 결과 검증 | 행 상한 1000, 음수 이상치 | 초과/음수 → 폴백 |
| 6 폴백 | `standard_aggregates` 5종 | 실패 시 대체 |
| 7 관측 | `trace_event` | 질문·SQL·폴백 기록 |
- 함수 화이트리스트 `ALLOWED_FUNCTIONS`={count,sum,avg,min,max,round,abs,substr,total}.

**3) 폴백 — ⚠️ 실측된 실제 동작**
- **관측 결과: 생성된 동적 SQL이 전부 `fellBack=True`.** 원인: LLM이 월별 추이에 `strftime()`를 쓰는데
  **`strftime`이 `ALLOWED_FUNCTIONS`에 없어** authorizer가 DENY → GuardrailError → 표준값(`variableMonthly`)으로 대체.
- 즉 **동적 T2SQL의 "결과 숫자"는 실제로 리포트에 안 쓰인다**(질문만 노출, 값은 표준 폴백).
- 반면 **표준 집계(`standard_aggregates`: SUM/GROUP BY/substr)는 정상 실행**(substr는 허용) → 리포트 ⑤의 월평균·고정·변동·주요지출은 **진짜 쿼리 결과**.

**4) 출력 → 리포트 ⑤** — `agents/report.py`
- `analyze_spending(pid,...)` → `SpendAnalysis(monthlyTotal, fixedMonthly, variableMonthly, topCategories, trend)`.
- P2 실값: 월평균 **2,739,982** / 고정 1,210,000 / 변동여력 1,529,982.
- `_feasibility_sentence(selected, spend)`: 선택 갈래 `monthlyBurden`(compare) vs `variableMonthly` 비교 문장 생성.

## N5. 개인화가 실제로 순위를 바꾸는가 (실행값)

| 실험 (P1 1인, 이사, 예산 3.6억) | 상위 결과 |
|---|---|
| 실측 override O(P1) | 성산동0.475·동선동1가0.405·중계동0.404 |
| 실측 override X | **동일** (P1 실측=세그먼트 둘 다 food high → values_food 같음) |
| 재택 진술 X | 성산동0.475·동선동1가0.405·중계동0.404 |
| 재택 진술 O(commute 0.5) | 성산동0.624·동선동1가0.58·중계동0.579 (**점수↑, 순서 동일**) |
| commute 1.6 / 0.4 / preference 1.8 | **상위5 전부 동일** |

**왜**: P1 이사 후보 8곳이 **전부 구 폴백**이라 통근·상권·선호 점수가 후보 간 동일 → 축 가중치를 바꿔도
순서 불변(차별 축은 예산=surplus뿐, 이건 개인화 안 됨).

**대조 (P2 신혼, 매매, 후보 차별화됨)**:
- 기본: 노고산동·쌍문동·방학동·… → commute 0.4: **방학동·쌍문동·도봉동·…** (**순서 바뀜**)

**판정**: 개인화 로직은 진짜로 점수를 바꾼다. 그러나 **상위3 재정렬은 후보가 차별화될 때만** 나타나고,
구 폴백이 많은 케이스(P1 이사)에선 개인화가 순위에 **안 보인다**(J5 동단위 데이터 커버리지 한계와 직결).
