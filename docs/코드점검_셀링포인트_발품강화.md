# 전체 코드 점검 지침 — 셀링포인트 관통 & 개인화 발품 강화
### 목표: "만기 → 3갈래 채점 → 개인화 하루 발품"이 하나의 흐름으로 느껴지게

> 이 지침은 기능 추가가 아니라 **기존 코드가 셀링포인트를 관통하는지 감사(audit)**하는 것.
> 코딩 에이전트에게: 아래를 순서대로 점검하고, 각 항목에 [OK/부족/누락] 판정 + 근거를 보고하라.
> **새 기능을 임의로 만들지 말 것.** 부족한 곳을 찾아 보고하면 사람이 우선순위를 정한다.

---

# PART 1. 셀링포인트 관통 감사 (3개 축)

## 축 1 — "만기라는 급성 순간"이 처음부터 끝까지 살아있는가
- [ ] SC-01 진입에 D-day·통보기한이 계산값으로 뜨는가
- [ ] 모든 화면 상단/컨텍스트에 "만기까지 N일"이 유지되는가 (사용자가 지금 급성 결정 중임을 계속 상기)
- [ ] 마지막 금융 연결·저장까지 "통보기한 전에 결정" 맥락이 이어지는가
- 판정 기준: 중간에 "만기"가 사라지고 그냥 "집 비교 서비스"처럼 느껴지는 화면이 있으면 [부족]

## 축 2 — "에이전트가 실데이터로 채점한다"가 보이는가
- [ ] 3갈래 숫자가 전부 실데이터/규정 기반인가 (하드코딩 잔재 grep)
- [ ] 각 숫자에 근거칩(출처)이 붙는가 — "그냥 계산기"가 아니라 "근거 있는 채점"으로 보이는가
- [ ] AI 브리핑이 "숫자를 읽어주고 해석"하는가 (단순 표 나열이 아니라)
- [ ] "AI가 확인한 것 / 확인 못 한 것" 구분이 노출되는가 (신뢰의 차별점)
- 판정 기준: 에이전트의 판단 흔적 없이 표만 뜨면 [부족]

## 축 3 — "개인화된 하루 발품"이 감동을 주는가 ★가장 중요·가장 약함
- [ ] 하루 발품이 그 사람 조건(가구형태·갈래·동네)에 맞게 달라지는가
- [ ] 발품 내용이 실데이터(상권·교통·실거래) 기반인가
- [ ] "숫자 나열"이 아니라 "하루의 서사"로 느껴지는가
- 판정 기준: P1(청년)이든 P2(신혼)든 똑같은 발품이 나오면 [부족] — 이건 반드시 [OK] 만들어야 함

# PART 2. 개인화 발품 강화 — 대상을 가르는 지점

> 현재 발품이 "동네에 카페 N곳" 수준이면 약하다. 아래로 끌어올린다.
> 원칙 유지: **사실(facts)은 실데이터, 서술만 LLM.** 지어내기 금지.

## 2-1. 발품에 들어갈 facts를 더 풍부하게 (있는 데이터 최대 활용)
현재 수집된 데이터로 더 뽑아낼 수 있는 facts를 점검:
- [ ] 교통: "○○역 도보 N분" + "직장/주요거점까지 대중교통 N분" (enrich 좌표 + ODsay/거리)
- [ ] 상권: 카페·음식점 수를 **"밀집도"로 해석** ("카페 47곳 — 걸어서 커피 고르기 좋은 동네")
- [ ] 실거래: 그 동네 **실제 최근 거래 사례** ("지난달 이 평형이 N억에 거래됐어요")
- [ ] 갈래별 차등: 매매=자산관점 발품 / 이사=생활환경 발품 / 갱신=아낀돈 발품
- [ ] 가구형태 차등: 1인=출퇴근·먹거리 / 신혼=평형·근린 / 자녀=학군·공원

## 2-2. 소비패턴 개인화 (마이데이터 자리 — PoC는 페르소나 프리셋)
- [ ] persona에 소비성향 필드가 있는가 (외식빈도·카페·차량보유 등)
- [ ] 그 성향이 발품 씬 선택에 실제로 반영되는가
    예: 카페 선호 페르소나 → "이 동네 카페거리" 씬 강조
        차량 보유 → "주차·대형마트 접근성" 씬 / 무차량 → "역세권·버스" 씬
- [ ] 규칙(scene_rules)이 공개되는가 (숨긴 가중치 없이 — "왜 이 씬인지" 설명 가능)
- 판정: 소비패턴이 발품을 실제로 바꾸지 못하면 [부족]

## 2-3. 발품의 "하루 서사" 구조 점검
- [ ] 시간 흐름(아침→저녁)으로 하루가 구성되는가
- [ ] 각 씬이 그 사람에게 의미있는 정보인가 (일반론 아님)
- [ ] 마지막에 비교표/예산으로 다시 연결되는가 (발품 → 결정 순환)

# PART 3. 데이터 보강 여지 점검 (있으면 발품이 풍부해지는 것)

> 아래는 "더 넣으면 좋은" 후보. 에이전트는 현재 확보/미확보를 판정만 하고,
> 신규 수집은 사람 승인 후 진행.

| 데이터 | 용도 | 확보 방법 | 우선순위 |
|---|---|---|---|
| 대중교통 소요시간 | "직장까지 N분" 발품 | ODsay API (좌표 있음) | 🔥 발품 핵심 |
| 실거래 최근 사례 | "지난달 N억 거래" 발품 | 이미 있음(trades.db) 활용 | 🔥 있는데 안 씀? |
| 생활물가 | "이 동네 물가 수준" | KOSIS/참가격 (구 단위) | 🟡 |
| 공원·녹지 | 자녀·여가 페르소나 발품 | 상권 API 여가분류 or 서울시 공원 | 🟡 |
| 학군 정보 | 자녀 페르소나 | 학교알리미 등 | 🟢 여력되면 |

- [ ] trades.db의 실거래를 발품에 쓰고 있는가? (수집만 하고 동네필터에만 쓰면 낭비 — 발품 facts로도 활용)
- [ ] ODsay 미연동이면 "직장까지 통근시간"이 발품에서 빠져있을 것 → 이게 개인화의 핵심인데 누락인지 확인

---

# PART 4. 흐름 연결부 점검 (조각 → 하나의 경험)

- [ ] SC간 전환이 "다음 단계로 자연스럽게 유도"되는가 (뚝뚝 끊기지 않는가)
- [ ] AI 브리핑이 각 화면을 이어주는 내레이터 역할을 하는가
    ("세 갈래를 봤으니, 매매를 고른다면 어떤 동네인지 볼까요?" 식 연결)
- [ ] 발품 끝 → 금융연결이 "이 하루를 현실로 만들려면" 맥락으로 이어지는가
- [ ] 전체를 관통하는 "OO님" 호칭·컨텍스트가 유지되는가 (개인화 일관성)

---

# 보고 형식 (에이전트 → 사람)
1. **축 1/2/3 각각 [OK/부족/누락] + 근거 파일·라인**
2. **가장 약한 고리 Top 3** (대상 수상 관점에서)
3. **"있는데 안 쓰는 데이터"** 목록 (trades.db 등 — 낭비 지점)
4. **개인화 발품을 풍부하게 할 구체적 제안 3가지** (기존 데이터로 가능한 것 우선)
5. 새 데이터가 필요한 경우만 별도 표기 (수집 리드타임 포함)

---

# 절대 원칙 (점검 중에도 유지)
- 숫자는 코드가, 서술만 LLM
- 발품 facts는 실데이터 (지어내기 금지)
- 특정 갈래·상품 추천 금지 (정보제공형)
- 새 기능은 제안만, 구현은 사람 승인 후
- "기능을 넓히지" 말고 "있는 흐름을 깊게"
